# 循环增殖实验版 alpha.1

## 启用与使用

客户端和服务端同时换成该实验版。首次测试使用测试世界或存档副本。实验执行默认关闭，管理员在游戏内运行：

```text
/eae2_pattern config set cycles.experimental_execution true
```

也可以在世界的 serverconfig/eae2_pattern-server.toml 中设置：

```toml
[cycles]
experimental_execution = true
```

将两条真实处理样板放入原供应器，机器配置和不消耗电路等仍按原方案预置。网络中放入启动材料和全部外部耗材，然后在原 AE2 终端请求循环中的 A 或 B。普通原生计划已能完成时不替换；仅原生缺料、捕获到受支持二元循环时尝试实验计划。成功时聊天显示阶段数，确认界面使用计划的全部初始耗材及字节开销；确认提交时原生 CPU 再次提取全部耗材，期间被其他任务取走则提交失败。

关闭开关只阻止新实验计划，已在运行的任务继续按保存状态执行。可通过 AE2 原生 CPU 界面取消；按原生取消机制退回 CPU 内现存材料，在途加工不会凭空回滚。切换回正式版、移除本模组或更换 AE2/CPU 实现前先完成或取消所有实验任务。

## alpha.1 支持范围

- 使用原生 CraftingCPUCluster 执行逻辑的 CPU；扩展其存储器/并行部件可以保留。网络包含尚未适配的独立 CPU 实现时，不产生实验计划，避免误交给另一套执行器。
- 两条原生 AE2 处理样板表示的 A→B、B→A 增殖回路，可附带其他消耗材料及确定性副产物。
- 请求目标必须是 A 或 B 本身，按本次新制作数量交付，并恢复所占用的启动库存。材料键严格区分物品、流体与 NBT。
- 必须保证样板声明的输出都会真实返回；概率输入按样板声明数量占用。概率返还或概率副产物不能作为可靠循环承诺，应先重新编码为准确的确定性输出，否则会停在等待材料状态。
- 外部耗材按整个计划的整数执行次数汇总，先要求已有库存；不自动制作缺失外部材料，不把未来副产物抵扣成现在可用库存。
- 采用可验证的完整整数周转量作为启动量，不保证找到数学上的最小启动组合。启动库存不足或计划超过 512 阶段/100 万次原配方执行时保留原生缺料结果。
- 存在已启用且接口匹配的 EAP 智能倍增时，单个实际投料批次最多合并 64 份原配方，并遵守其配置倍率上限；其他情况使用原版单份投料。供应器拒绝或能量不足时逐步缩小批次；同一批的实际产物全部回流后才发下一批。

尚不支持：上游 C 同时需要循环中的 A/B、一个任务的双交付目标、三种及以上材料回路、输入替代/返还容器、跨循环组联合规划、自动补种与机器故障恢复规划。纯数量核心已覆盖双目标算例，但运行时尚未接入双目标，不作功能承诺。

## 与 EAP 智能倍增的关系

新循环计划在原生缺料规划返回时单独构造，保留原注册配方身份，不把完整任务次数交给全计划倍增再合并。执行阶段通过 EAP 原有 PatternScaler 包装当前批次，沿用其输入输出放大和供应器解包逻辑；寻找供应器使用原配方，pushPattern 使用与实际输入量一致的批次配方。无法识别或关闭倍增时使用原配方单份投料，不把超量 inputHolder 强行交给普通供应器。普通非循环任务仍使用原生及附属模组原来的路径，不修改供应器倍增开关。该路径已经过字节码/API 核对，但 ExtendedAE、EAP、GTL 总成在游戏内的真实投料尚待验收，不等于所有附属供应器都已兼容。

## 必测场景

1. 小量启动 A，请求大量 A，观察 A→B→A 多轮，不能第一批就索要全量循环材料。
2. 改为从 B 启动；交换请求目标。启动量按完整整数周期准备。
3. 两条配方都消耗同一种 X，并带不同外部材料/流体：确认预览合计数量；取走一件必需 X 后重新规划，应该拒绝；确认界面打开后再取走 X，提交应失败。
4. 开启 EAP 智能倍增，比较任务仍按阶段推进；普通任务保持原行为。
5. 普通 AE2 与 ExtendedAE 供应器分别测试；小机器库存拒绝大批后应缩小投料，不扣丢 CPU 输入。
6. 单批只返回部分产物，应继续等待，不提前推进或交付。目标产物中途回流仍留在 CPU 内。
7. 等待回流时保存退出、重进，不能重复投料；断电恢复后继续同一阶段。外部存储满时最终交付等待容量。
8. 取消、机器阻塞、两个 CPU 同时发起请求，检查实际材料守恒；多个任务不能重复占用同一份启动材料。

## alpha.3：C 同时消费循环 A、B

支持 `A + X → 更多 B`、`B + Y → 更多 A`，以及 `mA + nB + Z → kC`。从原生 AE2 终端请求 C，记录其单层原生配方及循环路径；同时汇总两侧需求。若 C 每份产出 k，请求数量会按整份配方向上取整。

准备顺序是：占用启动材料、可用的 A/B 库存及全部外部 X/Y/Z → 增殖并凑齐 A/B → 执行 C → 实际回流后交付 C，退回剩余材料。不会把已经保留给 C 的 A/B 提前作为成品交付，循环外部耗材与 C 外部耗材缺一件都不启动。已有 A/B 可以直接用于转换或 C，避免无视库存而重复增殖。

当前只支持单层 C 直接依赖一个二元循环，C 可同时消耗 A/B，也可只消耗其中之一。C 支持无歧义、无返还容器的原生处理样板及普通合成样板；循环内仍限定两条确定性原生处理样板。更深的 C→D→循环链、多个循环、替代输入、自动制作缺少的外部材料仍不支持。

三配方任务使用状态格式 v2，旧二配方任务的 v1 格式继续读取。不能在未结束的三配方任务中降级旧版。启用开关、CPU 类型限制、附属倍增探测和 AE2CT 原生计划类型修复保持不变。实际 Forge 世界中的第三阶段投料和重载仍需验收。

alpha.3 构建通过：7097 项回归检查（含 C 双侧需求、原料缺一件、已有 A/B 抵扣、启动量保护及三阶段回流快照）、123 项通用包装/接口检查、37 项整合包接口检查。校验文件与版本元数据一致。未启动实际 Forge 世界。


## alpha.4：阶段内批量投料

处理配方按当前阶段剩余次数与 CPU 库存计算可发送次数，重复输入键先汇总，物品、NBT 与流体按原始键及单位计算。无额外固定 64 次上限，仍受总任务 1,000,000 次操作上限约束。

## alpha.6：GTL 总成原样板批量协议

对照 `others/mods` 中 GTLCore 的 `CraftingCpuLogicMixin.executeCrafting`、`AEUtils.extractForProcessingPattern`、`CraftingPatternPower.forCpu` 和 `MEPatternBufferPartMachineBase.pushPattern`：原生 CPU 对总成发送原始注册样板与多份 KeyCounter 材料。总成按样板查找槽位，然后把所有计数器交给内部槽位；临时倍增样板不是这个映射中的键，会被拒绝。这是 alpha.5 减量回退后只剩单份投料的具体接口缺口。

回流先进入 CPU 库存，整批返回后再推进；目标在所有阶段完成后统一交付，最终种子/副产物由原生 CPU 回存。保留整单外部耗材预算和提交复核，不承诺执行期间动态补料。

服务端在当前原生 CraftingPlan 附带快照，查询严格限定玩家当前 CraftConfirmMenu 和 containerId。客户端同时核对菜单实例及递增请求编号，旧回复不应用到新面板。服务端限每玩家 500ms 一次，客户端仅加载中每秒重试，最多 15 次；手动刷新可重新查询。数据超过 256 KiB 显示错误，不持续传输。普通无循环计划只返回无循环状态，不遍历全网配方。

执行计划与候选循环分别标识，后者不承诺可执行。当前只展示本模组识别/规划的循环，不是 AE2CT 通用合成树的完整替代。快照不会显示其他玩家的报告，默认关闭的聊天提示不影响查看。

客户端屏幕 Mixin 仅放在 client 列表，服务端仅加载菜单访问器。菜单字段和客户端构造签名进行 ABI 检查，不匹配时跳过适配。离线检查不等于实际游戏内视觉验证。更新协议 8 后客户端、服务端同步替换 jar 并重启。

## alpha.9：材料缺口

新增第四页“材料缺口”，每项显示图标/名称、总需求、规划时可用量和缺少量；缺料优先。物品按完整 AEKey（含 NBT）区分，流体保留单位。循环材料按工作库存预留量核算一次，外部原料按 A/B 所有阶段次数及下游 C 的用量合并预算，不把未来生产的 A/B 当成已存在库存。

外部耗材不足时保留核算快照，即使最终返回 AE2 的原生缺料计划也能查看。启动种子不足时显示 A、B 两种备选启动量，只需满足其一；此时阶段尚未确定，不展示伪精确的完整外部需求。每份核算给出对应循环路径，多候选时只显示最后检查的完整预算或选定可执行预算，不代表所有备选路线同时需要。

执行关闭时仍可核算受支持的循环，但不替换原生计划、不启动任务。配方不支持、接口不支持或无法生成阶段时显示未完成核算，不把未知缺口标成 0。此页不是仓库实时监控；补料后应返回 AE2 重新规划或重新发起请求。面板“刷新”只读取当前计划快照，不自行重新计算或消耗材料。提交时仍由 AE2 重新检查/提取库存。
